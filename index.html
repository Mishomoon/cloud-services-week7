3. Part A - Infrastructure as Code Questions

I selected four questions that are directly connected to my Week 7 work.

1. What is Infrastructure as Code, and which problems does it solve?

Infrastructure as Code means managing infrastructure such as virtual machines, networks, firewalls and storage through machine-readable configuration files instead of creating everything manually through a web console. The configuration can be stored in version control, reviewed and reused. This means that the code becomes a description of how the infrastructure should look.

This is especially clear when I compare my Week 1 and Week 7 work. In Week 1, I created the VPS manually. I had to remember the settings, configure the server and install the web server myself. If I had to rebuild the same server later, I would have to repeat those steps. There is also a risk that I would forget one setting or configure something slightly differently.

In Week 7, I wrote the infrastructure in OpenTofu. My configuration defines the VM, network port, security group, security group rules, managed key pair and floating IP resource. I also used cloud-init so that Apache and the webpage were configured automatically when the VM started. This made the process much more repeatable.

The destroy and rebuild experiment showed this practically. I ran tofu destroy and then tofu apply. Instead of manually creating the VPS again, OpenTofu recreated the resources from the configuration. The VM needed time to boot and for cloud-init to finish, but after that the webpage was working again.

IaC also helps with documentation and change tracking. Instead of only knowing that a security rule was configured somewhere in the cloud console, another person can inspect the configuration and see what the intended rule is.

2. Declarative vs. imperative automation and idempotency

Imperative automation describes the steps that should be performed. For example, an imperative script could say: create a security group, add an HTTP rule, create a VM, attach the security group and then configure the server. The focus is on the actions and their order.

Declarative automation is different because it describes the desired final state. Instead of telling OpenTofu every individual action, my configuration describes the resources that should exist. OpenTofu then compares the desired state with the current infrastructure and works out which changes are required.

The difference became clearer when I used tofu plan. I did not tell OpenTofu exactly how to modify the VM. I changed the configuration and OpenTofu calculated the required action. In one experiment it showed that the VM had to be replaced, while another change only required an in-place update.

Idempotency means that applying the same desired configuration again does not keep creating unwanted duplicates. Once the real infrastructure matches the configuration, running the configuration again should normally result in no unnecessary changes. I saw this when my configuration was already correct and tofu plan reported that there were no changes.

Idempotency is important because infrastructure automation may be run repeatedly. It makes automation safer and more suitable for automated workflows and CI/CD systems.

3. Why use OpenTofu instead of Terraform?

OpenTofu was created in 2023 as a fork of the last open-source (MPL-licensed) version of Terraform, after HashiCorp changed Terraform's license. OpenTofu and Terraform use a very similar Infrastructure as Code approach,so the configuration and workflow are familiar.I chose OpenTofu because it is an open-source, community-governed alternative to Terraform.

One important difference is licensing. HashiCorp changed Terraform's license from the Mozilla Public License (MPL) 2.0 to the Business Source License (BSL) 1.1. The BSL places restrictions on some commercial uses, especially products or services that compete with HashiCorp's products.

OpenTofu remains under the MPL 2.0 license and is governed as an open-source project under the Linux Foundation. This makes OpenTofu an attractive choice for organisations that want an open-source IaC tool without the same licensing restrictions.

For me, another advantage is that OpenTofu is community-governed rather than controlled by a single company. It also reduces the risk of being tied to one vendor's licensing decisions. The commands and workflow I used in this assignment, such astofu init, tofu plan, tofu apply and tofu destroy, worked well for managing my cPouta infrastructure.

References:

  • HashiCorp: Business Source License 1.1 — information about the BSL and competitive offerings.
  • Linux Foundation: OpenTofu Announces General Availability — information about OpenTofu as a community-driven project under the Linux Foundation.

4. What is the state file and why should it not be committed?

OpenTofu uses a state file to keep track of the relationship between the configuration and the real infrastructure. The state contains information about the resources that OpenTofu manages, including resource IDs and other attributes.

Without state, OpenTofu would have a much harder time knowing which real cloud resource belongs to which resource block in the configuration. For example, after I created my VM, OpenTofu needed to know that the VM already existed instead of trying to create a completely new one every time I ran the command.

The state file should not be committed to a public Git repository. It can contain infrastructure information such as IP addresses, resource IDs and, depending on the configuration and provider, potentially sensitive information. For this reason, my .gitignore includes rules for OpenTofu state files and personal variable files.

In a team, the state is normally stored remotely so that everyone is working with the same state instead of each developer keeping an independent copy on their laptop. A remote backend can also provide locking so that two people do not modify the same state at the same time.

For my individual Week 7 project, the important lesson was not to upload terraform.tfstate to my public GitHub repository. The configuration itself can be shared, but the local state should remain protected.

Resources and Files

OpenTofu Resources and Dependencies

My main.tf file describes the infrastructure needed for the Week 7 environment. The resources are connected through references, so OpenTofu can understand their dependencies and create or remove them in the correct order.

  • Project network data source: data.openstack_networking_network_v2.project finds the existing cPouta project network that the VM uses. The network is looked up rather than created by OpenTofu.
  • Floating IP resource and port association: openstack_networking_floatingip_v2.web creates and manages the public floating IP. Its port_id connects the floating IP to the network port used by the Week 7 VM, making the webpage publicly reachable.
  • Security group: openstack_networking_secgroup_v2.web creates and manages the security group used by the web server.
  • SSH rule: openstack_networking_secgroup_rule_v2.ssh allows SSH traffic on port 22 only from the CIDR address defined by ssh_allowed_cidr.
  • HTTP rule: openstack_networking_secgroup_rule_v2.http allows HTTP traffic on port 80 from the internet so that the webpage can be accessed publicly.
  • Network port: openstack_networking_port_v2.web creates the network port and connects it to the project network and the web security group. The VM uses this port for its network connection.
  • Key pair: openstack_compute_keypair_v2.week7 manages the OpenTofu SSH key pair named cloud-services-week7-iac-ed25519. The public key is read from ssh_public_key_path. The VM uses this OpenTofu-managed key pair.
  • VM: openstack_compute_instance_v2.week7 creates and manages the Linux VM. It uses the selected image, flavor, network port, security group and the OpenTofu-managed SSH key pair.

How the resources refer to each other:

  • The network port uses data.openstack_networking_network_v2.project and openstack_networking_secgroup_v2.web.
  • The VM uses the network port and openstack_compute_keypair_v2.week7.
  • The floating IP resource depends on openstack_networking_port_v2.web through its port_id argument. OpenTofu uses this reference to determine the creation and destruction order.

What each project file does

  • provider.tf: configures the OpenStack provider so OpenTofu can communicate with the cPouta cloud environment.
  • terraform.tfvars.example: provides example input variable values that can be copied to terraform.tfvars and adjusted for another cPouta project.
  • variables.tf: defines the input variables used by the configuration, including the instance name, image, flavor, network, key pair, SSH public key path and allowed SSH CIDR. ssh_allowed_cidr has a validation rule that rejects values that are not a valid CIDR address.
  • outputs.tf: defines the values displayed after tofu apply, including the instance name, private IP, public IP and webpage URL.
  • cloud-init.yaml: contains the VM's first-boot configuration. It installs Apache and Git, clones my public GitHub repository and copies the webpage files, screenshots and Week 1 PDF into the Apache web directory.
  • .gitignore: prevents local OpenTofu state files and personal variable files from being accidentally committed to Git.
  • main.tf: contains the infrastructure resources and the project network data source, including the security group, security rules, network port, managed key pair, floating IP resource and VM.

The cloud-init configuration also creates a dependency on my public GitHub repository. Because the VM clones the repository during its first boot, the repository must remain publicly accessible and must contain the index.html, screenshots folder and the Week 1 PDF used by the cloud-init configuration.

How to reproduce the setup

These steps explain how to recreate the Week 7 infrastructure using the OpenTofu configuration in this repository.

  1. Install OpenTofu on your computer.
  2. Download the OpenStack RC file from the cPouta dashboard and load it in your terminal. Enter your OpenStack password when prompted.
  3. Copy terraform.tfvars.example to terraform.tfvars.
  4. Update the values in terraform.tfvars for your cPouta project, network, SSH key and allowed SSH IP address.
  5. Open a terminal in the project folder and run these commands in order:
tofu init
tofu validate
tofu plan
tofu apply

Review the plan before confirming tofu apply. To remove the resources created by this configuration, run tofu destroy after checking the destruction plan.

8. Experiment 1 - Change and Replacement

Change 1 - cloud-init / user_data

I changed the cloud-init configuration used by the VM and then ran tofu plan.

Prediction: I predicted that changing the VM user_data would require the VM to be replaced, because cloud-init is used when the VM is created and the changed configuration needs to be applied to a fresh instance.

Result: My prediction was correct. The plan showed that openstack_compute_instance_v2.week7 had to be replaced. OpenTofu showed a destroy-and-create operation instead of an in-place update.

The reason is that user_data contains first-boot configuration. When it changes, the VM needs to be recreated so that the new cloud-init configuration can be applied during the new VM's first boot.

Change 2 - security group description

For the second change, I changed only the description of the security group. The actual SSH and HTTP rules were not changed.

Prediction: I predicted that this change would be updated in place because changing a description does not require the security group itself to be recreated.

Result: My prediction was correct. OpenTofu showed that the security group could be updated in place. The resource did not need to be destroyed and recreated.

This experiment showed me that not every configuration change has the same effect. A change to VM user_data caused a replacement, while a change to the security group description could be made in place.

9. Experiment 2 - Configuration Drift

For the drift experiment, I intentionally changed the security group description manually through the cPouta web interface.

The description was changed to: MANUAL DRIFT TEST

I did not change the OpenTofu configuration. This meant that the actual infrastructure and the declared configuration contained different values.

Prediction: I expected tofu plan to notice the changed security group description because the security group is managed by OpenTofu.

Result: My prediction was correct. OpenTofu detected the difference and showed that the security group description would be changed back to the value declared in the OpenTofu configuration. The security group could be updated in place rather than replaced.

However, tofu plan does not automatically detect every kind of manual change. For example, if I manually edited an Apache configuration file inside the VM through SSH, OpenTofu would not normally detect that file change because the Apache configuration file is not represented as a managed OpenTofu resource.

Another example would be creating a completely separate cloud resource manually through the cPouta web interface without adding it to the OpenTofu configuration or state. OpenTofu would not automatically manage that resource just because it exists in the cloud.

This is because tofu plan compares the declared configuration with the infrastructure information available through OpenTofu state and the provider. It is not a general scanner of everything that has been manually changed inside a VM or created outside the configuration.

The important lesson for me was that once infrastructure is managed with IaC, manual changes can cause the real environment and the code to become inconsistent. Keeping changes in the OpenTofu configuration makes the infrastructure easier to understand and reproduce.

10. Experiment 3 - Destroy and Rebuild

For Experiment 3, I tested whether I could destroy the infrastructure with tofu destroy and then recreate it with tofu apply.

Prediction: I expected OpenTofu to remove the resources according to their dependencies and then recreate them from the configuration when I ran tofu apply.

OpenTofu destroys resources according to their dependencies. Resources that depend on other resources must be removed before the resources they depend on. In this configuration, the floating IP is connected to the network port through port_id, so the floating IP must be removed before the port. The security group rules depend on the security group, so the rules must be removed before the security group. OpenTofu determines the order from the dependencies in the configuration, and independent resources may be destroyed in parallel.

Destroy result

I ran tofu destroy. OpenTofu destroyed all 7 managed resources, including the VM, managed key pair, floating IP, network port, security group rules and security group. 

Destroy complete! Resources: 7 destroyed.

Rebuild result

After the destroy operation, I ran tofu apply. OpenTofu recreated all 7 resources successfully. 

Apply complete! Resources: 7 added, 0 changed, 0 destroyed.

The new private IP address was 192.168.1.194. The public IP address remained 128.214.255.177.

The VM became active, but the webpage took about two minutes to work after the rebuild. Once the startup process finished, I confirmed that the webpage was accessible again.

This experiment showed that OpenTofu could destroy and recreate the infrastructure using my final configuration. It also showed that the webpage may need time to become available after the VM starts.

11. Security and Good Practices

I also considered security when creating the Week 7 infrastructure. The security group allowed HTTP from the internet because the webpage had to be publicly accessible. SSH was restricted to my own IP address instead of allowing SSH access from everywhere.

I also used .gitignore to prevent local OpenTofu state files and personal variable files from being accidentally committed. Private SSH keys must never be uploaded to a public GitHub repository. The same applies to passwords, cloud credentials, RC files and other secret values.

  • HTTP port 80 is public because the website needs to be reachable.
  • SSH port 22 is restricted to my own IP address.
  • OpenTofu state files are ignored by Git.
  • Personal .tfvars files are ignored.
  • Private SSH keys are not part of the public repository.
  • Cloud credentials and passwords should never be placed in the code.

12. Problems and Solutions

12.1 Understanding why a VM had to be replaced

One problem I had was understanding exactly which changes cause an OpenTofu resource to be replaced. Before applying the change, I used tofu plan to check what would happen when I changed the cloud-init configuration.

I predicted that changing the VM user_data would require the VM to be replaced because cloud-init is used during the VM's first boot.

The plan confirmed my prediction. The VM openstack_compute_instance_v2.week7 was marked as must be replaced. The solution was to read the plan carefully before applying changes so I could understand whether OpenTofu would update or replace a resource.

12.2 The webpage did not work immediately after rebuilding

Another problem happened during the destroy and rebuild experiment. After I ran tofu apply, the VM existed, but the webpage did not immediately respond.

At first this looked like an infrastructure problem, but the VM was still starting. cloud-init needed time to run its first-boot configuration. It had to install Apache, copy the webpage files and start the Apache service.

I waited for the startup process to finish and tested the webpage again. After cloud-init completed, Apache was running and the public webpage returned HTTP status code 200.

12.3 Understanding configuration drift

I also had to understand what would happen if the infrastructure was changed manually after it had been created by OpenTofu.

For the experiment, I changed the security group description through the cPouta web interface. The OpenTofu configuration still contained the original description.

When I ran tofu plan, OpenTofu detected the difference. The plan showed that the security group description would be changed back to the value from the configuration.

12.4 OpenStack CLI was not available on my computer

At one point I tried to use the openstack command-line client to inspect the floating IP. The command was not available in my Windows environment, so I could not use that command directly.

Instead of stopping the assignment because of this, I used the cPouta web interface and the information available from OpenTofu. I could still verify that the VM was running, that it had the expected networking and that the public webpage was reachable.

13. Reflection

Comparing Week 1 with Week 7, I found that the biggest difference was how the server was created. In Week 1, I created and configured the VPS manually. In Week 7, I described the infrastructure in OpenTofu and used cloud-init to configure the web server automatically.

At first, OpenTofu was more difficult for me because I had to understand resources, dependencies, state, variables and the difference between an in-place update and a replacement. For example, when I changed the cloud-init configuration, tofu plan showed that the VM had to be replaced. This helped me understand that OpenTofu does not simply edit every change on an existing server.

The main advantage I noticed was repeatability. Instead of manually configuring the server again, the configuration and cloud-init files describe how the infrastructure should be created. This made the destroy-and-rebuild experiment useful because I could use the same configuration again.

I also learned that security needs to be considered in the code. I restricted SSH access to my allowed CIDR address while HTTP was open because the webpage needed to be publicly accessible. I also used .gitignore to keep local state and personal configuration files out of Git.

I think manual server setup can still make sense when a quick one-time server is needed or when learning the basic steps. However, for infrastructure that needs to be reproduced, changed or maintained, Infrastructure as Code is more useful because the desired setup is written down and can be reused.

Overall, Week 7 helped me understand that Infrastructure as Code is not only about creating a VM. It is also about describing dependencies, controlling changes, keeping configuration reproducible and checking what OpenTofu plans to change before applying it.

One thing I noticed during the destroy and rebuild experiment was that the private IP changed to 192.168.1.194, while the public IP remained 128.214.255.177. OpenTofu destroyed all 7 managed resources and recreated all 7 successfully. Although the floating IP resource was destroyed and recreated, cPouta allocated the same public IP address again. The webpage took about two minutes to work after the rebuild while the VM and its startup configuration finished. This helped me understand that the private IP can change while the public IP can remain the same after a rebuild.

When each approach makes sense

Manual setup can make sense for a quick one-time server, for example when I am testing something or learning how a server works. It can be faster for a small task because I do not need to write configuration files first.

Infrastructure as Code makes more sense when infrastructure needs to be created repeatedly, shared with others, changed safely or rebuilt later. In my Week 7 project, OpenTofu made it possible to destroy and rebuild the infrastructure from the same configuration. It also made the intended settings easier to document and review.

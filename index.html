1. What is Infrastructure as Code, and which problems does it solve?

Infrastructure as Code means managing infrastructure such as virtual machines, networks, firewalls and storage through machine-readable configuration files instead of creating everything manually through a web console. The configuration can be stored in version control, reviewed and reused. This means that the code becomes a description of how the infrastructure should look.

This is especially clear when I compare my Week 1 and Week 7 work. In Week 1, I created the VPS manually. I had to remember the settings, configure the server and install the web server myself. If I had to rebuild the same server later, I would have to repeat those steps. There is also a risk that I would forget one setting or configure something slightly differently.

In Week 7, I wrote the infrastructure in OpenTofu. The configuration defined the VM, network port and security group. I also used cloud-init so that Apache and the webpage were configured automatically when the VM started. This made the process much more repeatable.

The destroy and rebuild experiment showed this practically. I ran tofu destroy and then tofu apply. Instead of manually creating the VPS again, OpenTofu recreated the resources from the configuration. The VM needed time to boot and for cloud-init to finish, but after that the webpage was working again.

IaC also helps with documentation and change tracking. Instead of only knowing that a security rule was configured somewhere in the cloud console, another person can inspect the configuration and see what the intended rule is.

2. Declarative vs. imperative automation and idempotency

Imperative automation describes the steps that should be performed. For example, an imperative script could say: create a security group, add an HTTP rule, create a VM, attach the security group and then configure the server. The focus is on the actions and their order.

Declarative automation is different because it describes the desired final state. Instead of telling OpenTofu every individual action, my configuration describes the resources that should exist. OpenTofu then compares the desired state with the current infrastructure and works out which changes are required.

The difference became clearer when I used tofu plan. I did not tell OpenTofu exactly how to modify the VM. I changed the configuration and OpenTofu calculated the required action. In one experiment it showed that the VM had to be replaced, while another change only required an in-place update.

Idempotency means that applying the same desired configuration again does not keep creating unwanted duplicates. Once the real infrastructure matches the configuration, running the configuration again should normally result in no unnecessary changes. I saw this when my configuration was already correct and tofu plan reported that there were no changes.

Idempotency is important because infrastructure automation may be run repeatedly. It makes automation safer and more suitable for automated workflows and CI/CD systems.

3. Why was OpenTofu created? Terraform vs. OpenTofu

Terraform was originally developed by HashiCorp and became one of the most widely used Infrastructure as Code tools. It uses HCL (HashiCorp Configuration Language) to describe infrastructure and uses providers to communicate with different platforms such as OpenStack, AWS, Azure and many others.

In 2023, HashiCorp changed Terraform's license from the Mozilla Public License to the Business Source License. Because of this change, community members and companies created a fork of the last open-source Terraform version. This project became OpenTofu.

OpenTofu keeps the same general idea and uses almost the same configuration language and workflow. In this course I used commands such as tofu init, tofu plan, tofu apply and tofu destroy. Someone familiar with Terraform will recognize the same workflow, with tofu used instead of terraform.

For my Week 7 project, the difference mattered mainly because I used OpenTofu. As a student, I could move between Terraform and OpenTofu concepts relatively easily because the configuration style and provider model are very similar.

4. What is the state file and why should it not be committed?

OpenTofu uses a state file to keep track of the relationship between the configuration and the real infrastructure. The state contains information about the resources that OpenTofu manages, including resource IDs and other attributes.

Without state, OpenTofu would have a much harder time knowing which real cloud resource belongs to which resource block in the configuration. For example, after I created my VM, OpenTofu needed to know that the VM already existed instead of trying to create a completely new one every time I ran the command.

The state file should not be committed to a public Git repository. It can contain infrastructure information such as IP addresses, resource IDs and, depending on the configuration and provider, potentially sensitive information. For this reason, my .gitignore includes rules for OpenTofu state files and personal variable files.

In a team, the state is normally stored remotely so that everyone is working with the same state instead of each developer keeping an independent copy on their laptop. A remote backend can also provide locking so that two people do not modify the same state at the same time.

For my individual Week 7 project, the important lesson was not to upload terraform.tfstate to my public GitHub repository. The configuration itself can be shared, but the local state should remain protected.

8. Experiment 1 - Change and Replacement

Change 1 - cloud-init / user_data

I changed the cloud-init configuration used by the VM and then ran tofu plan.

Before applying the change, I checked the plan to see what OpenTofu would do. The plan showed that the VM openstack_compute_instance_v2.week7 had to be replaced. The reason was that the user_data change forces the VM to be recreated.

The plan therefore showed a destroy-and-create operation rather than a simple update. This was useful because I could see the consequence of the change before actually applying it.

Change 2 - security group description

For the second change, I changed the description of the security group. I expected this to be less serious because the description does not change the actual network rules.

OpenTofu showed that the security group could be updated in place. The resource did not need to be destroyed and recreated.

9. Experiment 2 - Configuration Drift

For the drift experiment, I intentionally changed the security group description manually through the cPouta web interface.

The description was changed to: MANUAL DRIFT TEST

I did not change the OpenTofu configuration. This meant that the actual infrastructure and the declared configuration now contained different values.

I then ran tofu plan. OpenTofu detected the difference and showed that the security group description would be changed back to the value declared in the OpenTofu configuration.

The plan showed an in-place update rather than a replacement. This experiment gave me a practical example of configuration drift: the cloud environment had been changed manually, while the code still described the original desired state.

The important lesson for me was that once infrastructure is managed with IaC, making random changes through the cloud dashboard can cause the real environment and the code to become inconsistent.

10. Experiment 3 - Destroy and Rebuild

For the final experiment, I tested whether the infrastructure could actually be recreated from the OpenTofu configuration.

First, I ran tofu destroy. OpenTofu removed the resources that were managed by the configuration, including the VM, network port, security group and security group rules.

After the destroy operation, I ran tofu apply again. OpenTofu created the infrastructure again using the configuration. The new VM did not necessarily have exactly the same private IP address as before because the VM was recreated.

The webpage did not work immediately after the rebuild. At first, the VM was still starting and cloud-init was still working. Apache needed to be installed and started before the webpage could respond.

After waiting for the boot and cloud-init process to finish, I tested the webpage again. It became available and returned HTTP status code 200.

This experiment showed me the main benefit of Infrastructure as Code: I could destroy the managed infrastructure and rebuild it from the configuration without repeating the entire manual Week 1 process.

11. Security and Good Practices

I also considered security when creating the Week 7 infrastructure. The security group allowed HTTP from the internet because the webpage had to be publicly accessible. SSH was restricted to my own IP address instead of allowing SSH access from everywhere.

I also used .gitignore to prevent local OpenTofu state files and personal variable files from being accidentally committed. Private SSH keys must never be uploaded to a public GitHub repository. The same applies to passwords, cloud credentials, RC files and other secret values.

  • HTTP port 80 is public because the website needs to be reachable.
  • SSH port 22 is restricted to my own IP address.
  • OpenTofu state files are ignored by Git.
  • Personal .tfvars files are ignored.
  • Private SSH keys are not part of the public repository.
  • Cloud credentials and passwords should never be placed in the code.

12. Problems and Solutions

12.1 Understanding why a VM had to be replaced

One of the first problems I had was understanding the difference between changing a resource and replacing a resource. When I changed the cloud-init configuration, I initially expected OpenTofu to update the existing VM.

Instead, tofu plan showed that the VM must be replaced. The important part of the plan was the change to user_data, which forces the instance to be recreated.

The solution was to read the plan before applying it instead of assuming that every change would be made in place. The plan made it clear that OpenTofu would destroy the old instance and create a new one.

12.2 The webpage did not work immediately after rebuilding

Another problem happened during the destroy and rebuild experiment. After I ran tofu apply, the VM existed, but the webpage did not immediately respond.

At first this looked like an infrastructure problem, but the VM was still starting. cloud-init needed time to run its first-boot configuration. It had to install Apache, create the HTML file and start the Apache service.

I waited for the startup process to finish and tested the webpage again. After cloud-init completed, Apache was running and the public webpage returned HTTP status code 200.

12.3 Understanding configuration drift

I also had to understand what would happen if the infrastructure was changed manually after it had been created by OpenTofu.

For the experiment, I changed the security group description through the cPouta web interface. The OpenTofu configuration still contained the original description.

When I ran tofu plan, OpenTofu detected the difference. The plan showed that the security group description would be changed back to the value from the configuration.

12.4 OpenStack CLI was not available on my computer

At one point I tried to use the openstack command-line client to inspect the floating IP. The command was not available in my Windows environment, so I could not use that command directly.

Instead of stopping the assignment because of this, I used the cPouta web interface and the information available from OpenTofu. I could still verify that the VM was running, that it had the expected networking and that the public webpage was reachable.

13. Reflection

The biggest difference I noticed between Week 1 and Week 7 was the way the infrastructure was created. In Week 1, I manually followed the setup process and configured the server. In Week 7, I had to describe the infrastructure in code and let OpenTofu work out the changes.

At first, OpenTofu was more confusing than the manual setup because there were several new concepts to understand, such as resources, variables, state, providers, dependencies and the difference between in-place changes and replacement changes.

After I got the configuration working, I could see why IaC is useful. The configuration gave me a repeatable way to create the infrastructure. The destroy and rebuild experiment was especially useful because I could remove the managed resources and then recreate them from the same configuration.

The drift experiment was also important for my understanding. I manually changed a security group through the cPouta interface and then used tofu plan to see that the real infrastructure no longer matched the configuration.

I also learned that tofu plan is one of the most useful parts of the workflow. It lets me see what OpenTofu wants to change before I actually apply the change. This is especially important when the plan says that a resource will be replaced.

Overall, Week 7 helped me understand the practical difference between manual infrastructure and Infrastructure as Code. Week 1 taught me how to create and configure a VPS, while Week 7 taught me how to describe that infrastructure so that it can be checked, changed and recreated more systematically.
